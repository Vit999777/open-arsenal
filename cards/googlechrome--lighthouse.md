# Lighthouse — понять, что тормозит страницу VITTORA

- Исходный проект: https://github.com/GoogleChrome/lighthouse
- Направление VITTORA: сайт и журнал
- Дата проверки: 2026-10-30
- Степень проверки: documentation — изучена документация; установки, запуска и пилота нет.

## Что делает
Проверяет страницу в Chrome, собирает показатели загрузки и отчёт с замечаниями. Лабораторный замер означает запуск в заданных условиях, а не статистику реальных посетителей.

## Польза для VITTORA
Сценарий: страница музыки с трейлерами → исходный отчёт → выбор одной причины задержки → правка тестовой копии → повторный замер. Сейчас используются визуальный просмотр, проверка разметки и отдельных сценариев; этот обзор не подтверждает ни их полноту, ни наличие нового замера скорости. Lighthouse может дополнить их численными показателями, но не заменить просмотр композиции, прослушивание и проверку проигрывания.

## Главное преимущество
Для первого разового замера Lighthouse доступен прямо в Chrome DevTools: отдельный сервер измерений не требуется. По README он охватывает performance/accessibility/best-practices/SEO и экспортирует HTML/JSON. axe-core специализируется на доступности, Sitespeed.io — на более развёрнутых браузерных измерениях/видео/мониторинге. Это сравнение функций и порога входа, а не измеренная экономия или точность.

## Плюсы
- Показатели загрузки и диагностические замечания → материал для выбора конкретной правки, вместо впечатления «медленно».
- HTML/JSON и сохраняемые настройки → можно хранить исходный отчёт и сравнивать одинаковые серии.
- Локальный аудит в Chrome → не обязателен облачный сервис измерений. Загрузка самой страницы всё равно обращается к её серверам; отдельно есть добровольная отправка ошибок CLI.

## Запуск
- Сложность: просто для первого отчёта в DevTools; потребуется настройка для воспроизводимых серий. Это редакционная оценка: важно фиксировать версию, сеть, устройство, состояние кэша и исходную страницу.
- Где: компьютер с Chrome на поддерживаемой ОС. CLI main/package.json: Node >=22.19; README обобщает до Node 22 LTS+. Системная совместимость зависит от конкретной сборки Chrome/Node; GPU/AI-модель/API не нужны. Подтверждённого универсального минимума RAM/CPU в прочитанных источниках нет.
- Расходы: Apache-2.0 без лицензионной платы; модель/веса отсутствуют; локальный API/хостинг не обязательны. Остаются оборудование, сеть, электричество, диск для отчётов и труд. Полная денежная сумма и время неизвестны до выбора машины; потолок новых платных услуг пилота 0 ₽. Платные сторонние сервисы не подключаем.
- Лицензия: Apache-2.0 для кода, сохранить лицензию/уведомления и отмечать изменения при распространении; торговые марки и зависимости имеют отдельные условия. Полного аудита зависимостей не было.
- Как начать: Chrome → инструменты разработчика → Lighthouse → Generate report. Для воспроизводимого CLI позже закрепить версию пакета и Chrome; здесь установки нет.

| Sitespeed.io | README, MIT LICENSE, package.json Node>=22; release v42.10.0 от 23.10.2026; Docker либо браузер+Node, FFmpeg/Python для видео/визуальных метрик | Подходит для серий и расширенной диагностики, но больше настройки; сервер/Graphite/InfluxDB/Grafana нужны лишь при выборе соответствующего мониторинга |

У всех трёх локальный сценарий не требует платной регистрации; вычисления и труд не бесплатны по определению. Полные расходы альтернатив не измерены. Имена релизов из GitHub latest не доказывают версию встроенного в установленный Chrome Lighthouse. Все альтернативы оставлены для своих задач, не признаны некачественными.

## Состояние и ограничения
Проверены релизы и выборка открытых issues/PR 30.10.2026, не полный аудит:
- Lighthouse #17435 описывает проблему разложения времени LCP при имитации сети; #17438 обсуждает коэффициенты симуляции; PR #17439 предлагает изменение. Это сообщения участников, не наши результаты и не доказательство применимости к VITTORA.
- axe-core #5507 сообщает о пропуске части арабского текста при проверке контраста; PR #5508 предлагает исправление. Автоматическая проверка не гарантирует полную доступность.
- Sitespeed.io #4035 и PR #4926 обсуждают отражение даты baseline в метаданных сравнения. Заявленные авторами тесты не запускались нами.

## Когда не подходит
Баллы меняются от окружения и сети, поэтому одиночный прогон не доказывает улучшение. Не заменяет пользовательские замеры, полный SEO/юридический аудит доступности, проверку дизайна и работающего аудио/видео. Не исправляет сайт сам. Для специальных клавиатурных/экранных сценариев нужны ручной осмотр и axe-core. Закрытую страницу не открывать наружу ради проверки и не публиковать отчёты с секретами.

## Первый пилот
- Вход: разрешённая тестовая копия одной страницы музыки VITTORA с неизменным набором трейлеров; версия страницы и SHA исходников фиксируются перед началом.
- Действие: исполнитель по сайту (не назначен) фиксирует Chrome/Lighthouse, машину, сеть, кэш и профиль mobile; делает 5 последовательных прогонов, сохраняет локальные HTML/JSON. Разбирает одну воспроизводимую проблему, исправляет только тестовую копию, повторяет 5 раз.
- Метрика: медианы и диапазоны LCP (время появления основного содержимого), CLS (сдвиги макета), TBT (блокировка основного потока); отдельно размер страницы и конкретное замечание. Редакционный критерий для выбранной правки: снижение медианы LCP >=10%, CLS не выше исходного и ручной smoke-test проигрывания всех видимых плееров проходит. Если разброс не позволяет вывод — результат неопределённый, расширение только после оценки.
- Лимит: 60 минут, 0 ₽ новых услуг; RAM/диск/время записать фактически. Это бюджет эксперимента, не прогноз длительности.
- Откат: вернуть тестовую копию к исходному commit; production в этом пилоте не менять. Исходные медиа/отчёты сохранить.
- Результат: нет; машина/исполнитель/замеры не подтверждены.

## Кому ещё полезно
Авторам сайтов, журналов и небольших магазинов, которым нужно выбрать первую проблему загрузки для проверки.
