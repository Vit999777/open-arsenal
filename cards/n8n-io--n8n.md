## Что делает

n8n соединяет действия разных сервисов в схему. Error Trigger — узел, который получает сведения об ошибке связанной цепочки и начинает отдельную обработку сбоя.

## Польза для VITTORA

Предлагаемый сценарий: подготовка карточки журнала остановилась при проверке данных или обращении к сервису. Отдельная цепочка фиксирует название процесса, ошибочный шаг и ссылку на запуск, чтобы редактор мог разобраться. Это план применения, не результат испытаний.

Текущий подтверждённый процесс Открытого арсенала — GitHub-каталог, разборы, валидаторы и защищённый клиент Sites с журналом отправок. В случае неоднозначной отправки требуется сверка, а не автоматический повтор. n8n не заменяет эти ограничения. Фактическая n8n-конфигурация VITTORA в этом запуске не обследована: упоминание n8n в стеке не доказывает наличие нужной цепочки. Сначала инвентаризировать существующий экземпляр, прежде чем создавать второй.

Базовая линия будущего пилота — ручное чтение журнала тех же тестовых запусков и запись причины/шага в таблицу сравнения.

## Главное преимущество

По сравнению с ручным просмотром всех запусков связанный обработчик может направить сбои в отдельный процесс. Основание — официальная документация Error Trigger и исходник закреплённой версии. Уменьшение времени разбора и числа пропусков не измерено. Перед Activepieces/Huginn уникальное преимущество не доказано; n8n выбран по плану и для проверки конкретного механизма ошибок, отличного от утреннего сценария проверки полей.

## Плюсы

- Данные об ошибке → возможность построить запись о сбое, вместо общего «не получилось». Нужно заранее ограничить сохраняемые поля.
- Ссылка на неудачный запуск и lastNodeExecuted в примере кода → точка перехода к разбору. Состав фактических данных зависит от места сбоя и сохранения исполнения; полнота ещё проверяется.
- Самостоятельный запуск → контроль расположения данных и доступа, но резервирование, обновления и безопасность обслуживает VITTORA.

## Когда не подходит и существенные ограничения

- Официальная документация: Error Trigger срабатывает при ошибке автоматического связанного workflow. Запуск вручную не проверяет этот маршрут.
- Код2.46.6 при пустом ручном входе может вернуть пример с execution.id=231 и Example Error Message. Это образец, не факт реального выполнения. Не включать его в отчёт как успешный тест.
- Нужна явная связь исходной цепочки с обработчиком ошибок. Обработчик не является независимым монитором падения самого n8n, сервера или сети.
- Ошибки запуска trigger и ошибки последующих узлов могут иметь разный набор сведений. Ссылка/id могут отсутствовать; сохранять неизвестное, а не выдумывать.
- Журнал/stack/input могут содержать чувствительные данные: пилот синтетический, сохранять только разрешённые поля. Политика хранения и доступ должны быть настроены отдельно.
- Автоповтор операции публикации при таймауте может создать дубль. Не связывать тестовый обработчик с действующим Telegram/Sites и не обходить needs_reconciliation.
- Если существующий журнал уже закрывает задачу, дополнительный движок может увеличить обслуживание. Сначала обследовать текущий экземпляр.

## Первый пилот

- Исполнитель: технический специалист плюс редактор; конкретный человек не назначен.
- Вход: три синтетические карточки статьи с material_id и без персональных данных; копия тестовой схемы.
- После отдельного решения о запуске связать тестовую цепочку с Error Trigger на изолированном экземпляре. Запускать исходную цепочку входящим тестовым HTTP-запросом, а не кнопкой ручного выполнения. Новые расписания и внешние публикации не создавать.
- Проверить три контролируемых сбоя: отсутствующее обязательное поле, HTTP500 от локального тестового приёмника, таймаут этого приёмника. Отдельно одна карточка проходит без ошибки.
- Обработчик пишет только разрешённые сведения в тестовый приёмник: material_id, название цепочки, стадия, безопасный текст ошибки, фактический id/URL если есть. Не отправлять почту/Telegram.
- Цель редакции: 3/3 ошибок представлены в журнале обработчика, правильный шаг/причина в3/3 случаях, 0 ошибочных записей для успешной карточки, 0 внешних сообщений. Идентичность id сверять с реальным журналом исходной цепочки. Замерить задержку обработки и время поиска ошибки вручную, RAM/CPU/объём данных.
- Лимит: до60мин сверки после подготовки стенда, без новых расходов. Машина/лимит ресурсов/время подготовки пока не определены; сначала инвентаризация.
- Откат: отключить только тестовую связь и тестовый вход, сохранить результаты без секретов. Действующий процесс не изменять.
