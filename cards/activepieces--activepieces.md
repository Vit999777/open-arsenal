# Activepieces — проверка карточки перед передачей в редакционный черновик

- Проект: https://github.com/activepieces/activepieces
- Направление VITTORA: публикации и интеграции (publishing).
- Проверено: 06.11.2026, documentation; статус reviewing.
- Не установлено, не внедрено, пилота нет. Публикация blocked, [текст](../posts/2026-11-06_activepieces--activepieces.md).

## Что делает

Activepieces собирает действия сервисов в визуальную схему: принять данные, проверить условие, выбрать следующий шаг. HTTP — способ обмена запросами между программами; webhook — адрес, на который другая программа присылает событие.

## Польза для VITTORA

Предлагаемый сценарий: карточка статьи с material_id, заголовком, ссылкой на источник и статусом иллюстрации попадает в проверку обязательных полей. Полная карточка становится тестовым черновиком, неполная получает объяснение. Реальная публикация, подключение соцсетей и пересылка секретов в пилот не входят.

Текущий подтверждённый процесс Открытого арсенала — GitHub-каталог/разбор/пост, структурные валидаторы и защищённый клиент отправки с журналом. Activepieces его пока не заменяет. Наличие n8n в стеке пользователя не доказывает, что конкретная редакционная цепочка уже работает; её конфигурация здесь не прочитана. Для сравнения взять ручную проверку тех же карточек по одному списку полей.

## Главное преимущество

Визуальные ветви и сохранение версий схемы могут сделать передачу карточек понятнее редактору, чем разрозненные ручные действия. Основание — README: branches, HTTP, versioned flows. Экономия времени и снижение ошибок ещё не измерены. Перед n8n/Huginn уникального функционального преимущества не доказано; Activepieces выбран по ближайшему слоту и наличию CE под MIT вне явно исключённых модулей.

## Плюсы

- Ветвления → можно разделить полные и неполные карточки, сохранив причину отказа.
- Версии flow → можно зафиксировать вариант схемы для повторной проверки. Это не доказательство полного отката данных внешних сервисов.
- HTTP-шаги и собственные TypeScript-интеграции → возможность соединить сервис с программным интерфейсом. Наличие интерфейса не гарантирует совместимость, бесплатный API или право доступа.

Всё выше подтверждено документацией, а не рабочим результатом VITTORA.

## Запуск, сложность и полная стоимость

Нужен специалист: сервер, Docker Compose v2, приложение/worker, PostgreSQL и Redis, доступ, HTTPS, секреты, резервы и обновления. Документация self-host требует минимум 2 vCPU/4 ГБ RAM; на Windows — WSL2. Это требования авторов, не наши замеры. GPU и модели для проверки полей не нужны.

Прочитанный main/docker-compose.yml закреплён на 0.92.2, содержит pgvector:0.8.0-pg14, Redis7.0.7 и пять worker-реплик. Слепо запускать пример нельзя: требуется сверить исправленный релиз, ресурсы и число worker. Latest release API на дату проверки — 0.92.3-hotfix.2 от 28.10.2026.

В свежей инструкции manual path предлагается AP_EDITION=ee и активация лицензии, а README различает CE/MIT и Enterprise. Для предлагаемого CE-пилота не копировать EE-настройки: точный CE-пакет, режим исполнения и доступность нужных шагов в закреплённом релизе ещё проверить. Этот пробел оставляет reviewing. Опция hobby использует PGLite и очередь в памяти: документация предупреждает об одной машине, отсутствии масштабирования и переходе с началом заново. Её нельзя выдавать за производственный эквивалент PostgreSQL/Redis.

Полная стоимость:
- CE-код вне исключений — без лицензионного платежа; Enterprise — коммерческая лицензия, не выбран.
- Сервер/CPU/RAM, диск PostgreSQL/Redis, сеть, домен/HTTPS, хранение и проверка восстановления резервов.
- Работа: выбор релиза, настройка схем, обновления, мониторинг очередей, права доступа, расследование ошибок и защита от повторов.
- Модели/веса и платный AI API не требуются для выбранного пилота. AI-узлы и сторонние интеграции могут потребовать отдельные ключи, тарифы и лимиты.
- Облако и коммерческие тарифы не исследованы, аккаунты не создавались. Рублёвая сумма, имеющаяся машина, фактическая память и трудозатраты неизвестны.

## Когда не подходит

Если текущий клиент GitHub/Sites уже решает единственную задачу, второй движок добавит обслуживание. Автоповторы HTTP не гарантируют отсутствие дублей: операции записи требуют устойчивого ключа material_id и атомарного запрета повторной записи на стороне получателя. Этот механизм не подтверждён готовым.

Прочитанный Catch Webhook main по умолчанию authType=none; предусмотрены Basic/Header/HMAC. Перед реальными данными выбрать проверяемую авторизацию. Возможности main и конкретного релиза могут отличаться. Не подключать production webhook и сторонние аккаунты до проверки. Секреты, персональные сведения и содержимое подключений не помещать в открытый каталог или логи.

## Первый пилот

- Ответственный: технический специалист и редактор; конкретный исполнитель пока не назначен.
- Материал: 5 синтетических карточек, 3 полные и 2 с отсутствующими обязательными полями, плюс 3 повторные доставки одной полной карточки.
- В изолированном CE-стенде проверить ветку валидации и запись в тестовый приёмник черновиков. Никакой Telegram/почты/производственных очередей. Отдельно задать и проверить защиту приёмника по material_id.
- Цель: 3 уникальных черновика, 2 понятных отказа, 0 новых черновиков от 3 повторов; 100% совпадение переданных полей с эталоном; 0 внешних отправок. Записать время ручной проверки и схемы, RAM/CPU и прирост БД.
- Лимит редакции: до60мин проверки после подготовки стенда, без покупок и новых платных аккаунтов; машина/ресурсный лимит и срок подготовки неизвестны. Запуск не выполнялся и этим обзором не разрешается.
- Откат: выключить только тестовый flow, сохранить результаты без секретов; действующий процесс GitHub/Sites остаётся базовой линией.
- Если CE-режим или защита повторов не подтверждены — зафиксировать неуспех и оставить reviewing.

## Кому ещё полезно

Небольшим редакциям и командам, которые передают структурированные карточки между сервисами и готовы обслуживать отдельный сервер.
