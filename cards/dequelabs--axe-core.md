# axe-core — найти проблемы доступности сайта VITTORA

- Исходный проект: https://github.com/dequelabs/axe-core
- Направление VITTORA: сайт и журнал
- Дата проверки: 2026-10-30
- Степень проверки: documentation — изучена документация; не установлен, пилот не проведён.

## Что делает
Проверяет показанную в браузере страницу по правилам доступности: например, контраст текста, подписи полей и кнопок, корректность структуры. Возвращает список замечаний с элементами и объяснениями. Доступность — возможность пользоваться сайтом людям с разными способами восприятия и управления; один автоматический отчёт её не гарантирует.

## Польза для VITTORA
Предполагаемый сценарий: тестовая копия страницы музыки с плеером и формой подписки → проверка обычного вида, открытого меню и формы с показанной ошибкой → ручная сверка → одна адресная правка. Проверять форму только с искусственными данными и отключённой реальной отправкой. Текущее визуальное наблюдение/проверки разметки и обзор Lighthouse дают другой срез; axe-core может добавить повторяемые проверки конкретных состояний. Наличие рабочего автоматического контура в VITTORA этим обзором не подтверждается.

## Главное преимущество
По API.md можно запускать проверку в существующей тестовой среде после каждого изменения видимого состояния и получать структурированный результат. По сравнению с одноразовым взглядом на скриншот это даёт список элементов и правил для разбора; выигрыш времени/качества ещё не измерен. В отличие от Pa11y axe-core — само ядро, а не готовый запускатель браузера. Pa11y умеет использовать axe-core, поэтому это не независимая гарантия качества и не два полностью разных проверяющих механизма.

## Плюсы
- Привязка результата к элементам и helpUrl → разработчику проще найти место правки и объяснение; API возвращает JSON.
- Проверки можно повторить после раскрытия меню/диалога → не ограничиваться начальной страницей. Скрытое содержимое не проверяется до показа.
- Локальная работа в современном браузере → сторонний сервер обработки не обязателен. Сама страница и открываемые справочные ссылки всё равно могут обращаться к сети.

## Запуск
- Сложность: потребуется настройка, редакционная оценка. Нужно добавить библиотеку в тестовую страницу/среду, вызвать axe.run(), дождаться появления интерфейса и разобрать результат; это не пользовательская программа с одной кнопкой.
- Первый шаг: выбрать одну разрешённую тестовую страницу, подключить закреплённую версию axe-core как зависимость разработки, вызвать axe.run() после её загрузки; сохранить violations и incomplete, затем повторить после раскрытия меню/ошибки формы.
- Среда: компьютер с современным Chrome/Firefox/Edge/Safari. README говорит о современных браузерах; постоянно на PR проверяются Chrome и Firefox. ОС/ресурсы зависят от выбранного браузера и тестового окружения. package.json содержит engines node >=4, но это не рекомендация устаревшего Node и не требование всей актуальной сборочной среды. Для разработки нужен поддерживаемый Node; минимальная версия всего контура и машина ещё не выбраны.
- GPU, AI-модели и облачный API не требуются. Полезный минимум RAM/CPU и диск в первоисточниках не нормированы для нашего сценария.
- Расходы: код MPL-2.0 без лицензионной платы; отдельной модели/весов нет; в локальном сценарии платный API/хостинг не обязательны. Остаются машина, электричество, сеть, хранение отчётов и труд разработчика. Полная сумма/время неизвестны до пилота. Бюджет новых услуг — 0 ₽; ничего не покупали.
- Лицензия: Mozilla Public License 2.0. При распространении изменённых покрытых файлов нужны выполнение условий MPL и доступность соответствующего исходника; включение в больший проект само по себе не переводит весь чужой код под MPL. MIT/ISC notices встроенных зависимостей перечислены в LICENSE-3RD-PARTY.txt, их условия сохраняются отдельно. Торговые марки не предоставляются автоматически; полного аудита цепочки зависимостей не было.

## Состояние поддержки и риски
Изучена выборка открытых issues/PR, не весь трекер:
- axe-core #5507 сообщает о пропуске части арабского текста в проверке контраста; PR #5508 предлагает исправление, PR #5509 — изменение проверки названий во вложенных группах. Это заявления участников, не наши воспроизведения. Даже README оговаривает ошибки и ручную проверку incomplete.
- Release v4.14.0 предупреждает: изменения правил и исправления могут как поднять, так и снизить число замечаний. Сравнивать результаты при закреплённой версии; заявленные авторами ускорения не переносим на VITTORA.
- Pa11y #617 / PR #872 обсуждают экспорт встроенных отчётов для JavaScript; PR #871 — обработку запуска с ignoreUrl. Заявленные в PR тесты нами не запускались.
- HTML_CodeSniffer #325 сообщает о пропуске input type=url, PR #326 — добавление перевода; это не основание объявлять весь инструмент непригодным.

## Когда не подходит
Не гарантирует полноту WCAG, законное соответствие или удобство интерфейса. Проверяет только отображённые состояния; без ручного открытия скрытое меню/диалог пропустится. JSDOM поддержан ограниченно, color-contrast там не работает: для контраста нужен реальный браузер. Нужны ручные клавиатурные прогоны, проверка фокуса, чтение экранным диктором и смысловая оценка текста. Ошибки в сообщениях возможны. Не использовать счётчик нарушений как метрику дохода, охвата или полной доступности.

## Первый пилот
- Вход: одна тестовая копия страницы музыки VITTORA с плеером/меню/формой; искусственные данные, реальная отправка формы выключена.
- Исполнитель: разработчик сайта, пока не назначен. До запуска записать commit страницы, Chrome/axe-core, машину, размеры экрана и настройки правил.
- Действие: сохранить JSON и скриншоты трёх состояний: начальный вид, раскрытое меню, форма с показанной ошибкой. Вручную разобрать violations/incomplete, исправить один подтверждённый дефект в тестовой копии и повторить.
- Метрика: редакционный критерий — результаты сохранены для 3/3 состояний; одна вручную подтверждённая ошибка устранена и исчезает при повторе с теми же настройками, новых serious/critical нет. Если ошибок не найдено, записать «не найдено в этих состояниях», а не «сайт доступен». Отдельно пройти 5 действий клавиатурой: переходы к меню, плееру, запуск/пауза, полю, обратному закрытию меню; записать 5/5 или конкретный провал. Это ручная метрика, не обещание axe-core.
- Лимит: 60 минут и 0 ₽ новых услуг, CPU/RAM/размер отчётов измерить; полные затраты пока неизвестны.
- Откат: вернуть тестовую копию к исходному commit; не менять production и исходные медиа.
- Результат: отсутствует; установку и пилот не проводили.

## Кому ещё полезно
Авторам журналов, сайтов книг, небольших магазинов и разработчикам форм/плееров, которым нужна проверка отдельных состояний интерфейса.
