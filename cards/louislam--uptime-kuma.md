# Uptime Kuma — контроль доступности страниц VITTORA

- Исходный проект: https://github.com/louislam/uptime-kuma
- Направление VITTORA: reliability — надёжность
- Дата проверки: 2026-10-31
- Степень проверки: documentation, только источники; не установлен, пилот не выполнен.
- Редакционный статус: reviewing. Публикация обзора не означает внедрение.

## Что делает
С заданным интервалом запрашивает страницы и записывает, отвечают ли они. Может проверять наличие заданного слова в ответе и выдавать уведомления.

## Польза для VITTORA
Рассматриваем наблюдение за главной, музыкой и журналом с отдельной машины. Сценарий: вместо случайного обнаружения недоступной страницы иметь историю проверок. Текущий процесс по доступному контексту — отдельные ручные проверки и периодические аудиты; наличие работающего круглосуточного монитора не подтверждено. Время обнаружения и стоимость текущего процесса не измерены. Это предложение, не полученный результат.

## Главное преимущество и сравнение
Кандидат выбран по вечернему слоту 31.10, без замены. Основное преимущество для редактора — настройка проверок через экран, тогда как Gatus ориентирован на разработчиков и текстовую конфигурацию. Основание — README обоих проектов, не сравнительный тест.

| Вариант | Подтверждено источниками | Почему выбран/отложен |
|---|---|---|
| Uptime Kuma | HTTP, Keyword, JSON, история, экран настройки, MIT | Подходит для страниц и редактора; пилот с проверкой известной проблемы 2.5.8 |
| Gatus | HTTP/код/тело/время ответа; YAML-конфигурация; Apache-2.0 | Лучше рассмотреть для правил в git; нужен специалист по конфигурации. Текущий go.mod: Go 1.26.3 для сборки; есть Docker |

| Ручной осмотр | Уже используется в обсуждениях VITTORA | Видит поведение плеера/формы; не даёт постоянной истории. Время не измерено |

## Плюсы
- HTTP Keyword проверяет нужное слово → можно различать нормальную страницу и ответ без ожидаемого содержимого; не равнозначно проверке работающего интерфейса.
- История/график → материал для сверки времени сбоя.
- Экран настроек → редактору не требуется писать YAML для каждой проверки.
- Self-hosted → можно размещать на своей машине; это добавляет обязанность обслуживания, а не доказывает экономию.

## Запуск
- Сложность: потребуется настройка (редакционная оценка): постоянно работающая машина, хранение данных, закрытый доступ к админке и проверка уведомлений.
- Среда: Docker либо Linux/Windows; для стабильной 2.5.8 package.json требует Node >=20.4.0, Git, README рекомендует pm2.
- Важно: master уже 3.0.0-beta.0 и engines Node >=26.2.0; не смешивать требования master и стабильной версии. Пилот закрепляет релиз, не исполняет команды master вслепую.
- Данные: локальный каталог/volume; README прямо исключает NFS.
- RAM/CPU/диск для трёх проверок не измерены; подтверждённый минимум не установлен этим исследованием. GPU и модели для HTTP-мониторов не нужны.
- Полная стоимость: код без лицензионной платы; свои компьютер/сервер, электричество, сеть, диск, резерв данных, обновления и время специалиста; отдельные службы уведомлений могут иметь свои тарифы. Точный бюджет неизвестен до выбора машины и канала. Платные API для локальной HTTP-проверки не требуются. Покупок/регистраций/установок нет.
- MIT: сохранять copyright и текст разрешения в копиях/существенных частях; гарантий нет. Зависимости имеют отдельные условия, полный аудит зависимостей не проведён.

## Когда не подходит
- Нет отдельной постоянно работающей машины: монитор на выключенном компьютере бесполезен.
- Проверка из той же отказавшей инфраструктуры не докажет доступность извне.
- HTTP 200/слово не доказывают проигрывание аудио, отправку формы или корректность закрытого центра. Закрытые страницы могут вернуть вход вместо содержимого; не добавлять секреты ради этого обзора.
- В latest 2.5.8 issue #8078 сообщает о белом экране публичной status page; это сообщение автора issue, не воспроизведённый нами дефект. В пилоте не полагаться на публичную status page.
- Release 2.5.8 включает security fix GHSA-v2p3-6f5h-6hhf и удаление TLS из TCP monitor; TCP-проверка не заменяет HTTPS-проверку.
- MariaDB issue #8084: отказ при отсутствии права CREATE DATABASE; для первого пилота внешнюю БД не подключать.
- Push issue #8087 описывает отсутствие повторного оповещения при повторном DOWN; не трактовать каждое событие как отдельную гарантированную доставку.

## Первый пилот
- Вход: отдельная тестовая страница с публичным синтетическим текстом VITTORA и управляемыми ответами; без персональных данных.
- Ответственный: технический исполнитель VITTORA, назначение пока не подтверждено.
- Действие: на отдельно выбранной машине закрепить согласованный стабильный релиз; добавить HTTP + Keyword, интервал 60 секунд; выполнить 3 цикла 200 → 503 → 200 и один ответ 200 без нужного слова. Основной сайт не отключать. Уведомления сначала в локальном журнале; никакой отправки в другие каналы.
- Метрика: все 3 отказа/восстановления и отсутствие слова отражены в журнале; целевой порог обнаружения <=120 сек при выбранном интервале (редакционный критерий, не гарантия). Записать задержку, ложные тревоги, RAM, CPU и размер данных за 24 часа.
- Отдельно проверить открытие dashboard и status page для #8078; сохранить фактический результат.
- Лимит: один тестовый endpoint, одна машина, 24 часа; бюджет оборудования ещё не согласован, платные ресурсы не выделять.
- Откат: остановить тестовый монитор, сохранить журнал, вернуться к ручным проверкам. Рабочую конфигурацию сайта не менять.

## Кому ещё полезно
Владельцам сайтов, небольшим редакциям и администраторам, которым нужна история доступности нескольких страниц.
