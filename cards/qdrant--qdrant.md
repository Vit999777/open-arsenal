# Qdrant — найти нужный фрагмент в знаниях VITTORA

- Исходный проект: https://github.com/qdrant/qdrant
- Направление: агенты/RAG (agents_rag).
- Проверка: 2026-10-29, documentation; без установки и пилота.
- Версия для будущего пилота: [v1.20.0](https://github.com/qdrant/qdrant/releases/tag/v1.20.0), опубликована 22.10.2026.
- Каталог: reviewing. Полная стоимость, модель и рабочая машина неизвестны.

## Что делает
Хранит числовые представления материалов (векторы) и находит близкие к запросу. Для смыслового поиска отдельная модель должна сначала преобразовать фрагменты и вопрос в такие числа. Qdrant сам не пишет достоверные ответы и не создаёт готовую базу знаний из папки файлов.

## Польза для VITTORA
Предлагаемый сценарий: 30 разрешённых фрагментов книги, журнала и редакционных инструкций → поиск по вопросу → три фрагмента с сохранёнными URL/версией/названием источника для ручной проверки. Метаданные проектируем мы; достоверность ссылки не гарантирует сама база.
Сейчас подтверждены разрозненные материалы и запрос на рабочую память агентов; работающий единый смысловой поиск VITTORA не подтверждён. Базовая альтернатива — ручной поиск по названиям и ключевым словам. Его время и точность тоже нужно измерить.
В пилот не загружаются секреты, личные переписки, доступы или непроверенные на разрешение документы. Не создаём облачные аккаунты и не переносим производственные базы.

## Главное преимущество
Документированная связка поиска по векторам и фильтрации полей (payload) в отдельном сервисе. Для смешанного корпуса можно хранить тип материала, версию и ссылку и фильтровать книгу отдельно от инструкций. Это преимущество структуры относительно поиска только по именам файлов; выигрыш скорости/точности не измерен.
Если нужные тексты уже живут в Postgres, pgvector может оказаться проще по эксплуатации: отдельный сервис Qdrant не является обязательным условием RAG (поиска источников для ИИ).

## Плюсы
- Смысловая близость → возможность находить фрагмент при другом выражении вопроса; реальное качество зависит от модели, языка и разбиения текста.
- JSON-поля и фильтры → отделение типов/версий материалов; обычный фильтр не заменяет проверку прав доступа приложением.
- Возврат payload вместе с результатом → можно показать сохранённый источник рядом с цитатой.
- Локальная установка и API → свой контур хранения и возможность подключить приложения. Это будущая интеграция, она не выполнена.

## Запуск
- Сложность: нужен специалист — редакционная оценка. Требуются подготовка корпуса, выбор/лицензирование модели, преобразование текста, загрузка, API запросы и приёмка результатов.
- Где: свой компьютер или сервер с 64-bit x86_64/arm64 и контейнерной средой. Qdrant требует блочное хранилище с POSIX-совместимой файловой системой; NFS/S3 не подходят как основной storage. RAM/CPU зависят от числа/размерности векторов, индексов и payload. Конкретные RAM/диск/время для VITTORA не измерены.
- В документации отмечены проблемы файловых систем Docker/WSL на Windows при mount, вплоть до потери данных. Рабочую среду нужно выбрать до пилота.
- Базовый первый этап после отдельной подготовки среды: контейнер фиксированного v1.20.0 с привязкой HTTP только к 127.0.0.1, отдельным постоянным каталогом и без внешнего доступа. Не копировать открытый на все интерфейсы README quickstart как производственную конфигурацию.
- Локальные сокеты/API не означают облачную плату. Для выбранного базового векторного поиска GPU не обязателен; аппаратные требования выбранной embedding-модели пока неизвестны.
- Локальный API/ключи, TLS, доступ и резервирование для production ещё не настроены. Существующие ключи не создавались/не ротировались; инструменты проекта не внедрялись.
- Модель не выбрана: язык русский, лицензия весов, версия, размерность, RAM и условия зависимостей должны быть проверены отдельно. В пилоте используем заранее подготовленные локальные векторы только после этой проверки. Не выдаём Apache-лицензию базы за лицензию модели.

## Полная стоимость и лицензии
- Код Qdrant: без лицензионной платы за локальный open-source вариант, Apache-2.0; соблюдать уведомления/лицензию при распространении, отметить модификации. Полный аудит зависимостей не выполнен.
- Модели/веса: отдельная лицензия и загрузка; не выбраны, цена и ресурсы неизвестны.
- Вычисления: RAM/CPU/диск/электричество/труд подготовки и сопровождения нужны, фактическая сумма неизвестна.
- API: внешнее платное API не требуется, если эмбеддинги подготовлены локально; цена внешнего провайдера не оценивалась, пользоваться им не разрешено в этом пилоте.
- Хостинг: для локального пилота не нужен; аренда/управляемое облако оплачиваются отдельно и не выбирались. Не заявляем тариф облака.
- Новые услуги/покупки: лимит 0 ₽, аккаунты не создавались. Нулевой чек не означает нулевую общую стоимость.
- Chroma Apache-2.0 и pgvector PostgreSQL License не покрывают автоматически модели, документы и другие зависимости.

## Когда не подходит
Для 30 фрагментов простой поиск по словам может оказаться достаточным; решение о внедрении только после сравнения. Qdrant не гарантирует истину, не извлекает текст/OCR автоматически в нашем сценарии, не пишет готовые ответы и не управляет правами на исходники сам по себе.
Если у документа изменилась версия, индекс и ссылка должны быть обновлены; поиск похожего не доказывает актуальность. Качество русского поиска ещё неизвестно.
README и security прямо предупреждают: self-hosted конфигурация по умолчанию открыта на все интерфейсы и без аутентификации. В production нужны явные настройки. Доступы текущего центра VITTORA не менять.

## Релизы и замечания пользователей
v1.20.0 добавил BM25 для full-text payload, TurboQuant и другие изменения по release notes. В обзоре не обещаем результаты этих оптимизаций.
Issue #11326 сообщает о пустых результатах TurboQuant+Euclid при больших конечных числах в 1.20.0. Не воспроизведено нами; первый пилот не использует TurboQuant.
Issue #11330 — ограничение формулы geo_distance с несколькими точками; геоданные не входят в сценарий.
PR #11332 — предложенная правка удаления каталогов Windows (описывает 1.19.1); нельзя утверждать, что исправление уже входит в выбранный релиз.
Chroma PR #7968 касается валидации JS-входа, #7967 — зависимостей standalone WAL. Это сообщения авторов PR, не наш аудит безопасности.
pgvector #1043 сообщает об особом случае Jaccard all-zero bit, #1042 — план 0.9.0; для пилота не выбираем бинарную Jaccard и не считаем будущую версию выпущенной.

## Первый пилот
- Вход: 30 разрешённых фрагментов VITTORA с ID, URL/путём, версией, SHA-256 и типом материала; 10 вопросов с заранее назначенным правильным источником. Два дополнительных вопроса вне корпуса — для ручной проверки отсутствия основания отвечать.
- Исполнитель: технический редактор/инженер VITTORA; конкретный человек и машина не назначены.
- Этап допуска: выбрать локальную русскоязычную embedding-модель, проверить лицензию/ресурсы и назначить машину. Без этого смысловой пилот не начинать.
- Действие: один и тот же корпус/вопросы сравнить с поиском по словам, затем Qdrant top-3 с payload и фильтром типа. Генерацию ответов ИИ не включать.
- Метрика: релевантный заранее размеченный источник есть в top-3 минимум в 8 из 10 вопросов; сохранённые ссылки/версии корректны в 10/10. Записать ложные совпадения, время подготовки/запроса, RAM, размер индекса и результат baseline. Это редакционный порог, а не достигнутый результат.
- Не выдавать nearest match по вопросам вне корпуса за достоверный ответ. Порог отказа ещё не откалиброван, решение в пилоте принимает проверяющий.
- Лимит: 30 фрагментов, одна сессия до 60 минут после допуска модели, 0 ₽ новых услуг. RAM/диск проверить до старта; бюджет ресурсов неизвестен.
- Откат: отдельный локальный каталог и индекс, оригиналы не менять, производственные сервисы не подключать; при провале оставить ручной поиск.

## Кому ещё полезно
Авторам, редакциям и командам, которым нужно находить источники в собственной базе материалов.
